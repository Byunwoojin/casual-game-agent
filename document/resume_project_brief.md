# 캐주얼 게임 에이전트 프로젝트 — 이력서 작성용 브리핑 문서

> 이 문서는 이력서/포트폴리오 문구를 작성해줄 Claude(또는 다른 사람)에게 그대로 전달하기 위한 사실 기반 요약이다.
> 프로젝트 원문서(`document/casual-game-agent-design.md`, 368줄)를 압축·재구성했으며, 여기 적힌 수치는 전부 실제 파일/테스트 결과에서 나온 것 — 과장 없이 그대로 사용 가능.

## 한 줄 요약

Unity 기반 캐주얼 퍼즐 게임 4종(직소/틀린그림찾기/슬라이딩 퍼즐/메모리 매칭)을 순차적으로 직접 구현하면서, 그 과정에서 실제로 재사용된 코드와 반복된 절차를 근거로 "공통 프레임워크(Core Spec) vs 장르별 규칙(Game Rule Spec)"을 실증적으로 분리해내고, 프로젝트 부트스트랩과 배치모드 자동 검증(컴파일/유닛 테스트/디스플레이 없는 E2E 테스트)을 스크립트로 자동화한 개인 프로젝트.

## 프로젝트 배경 / 문제의식

캐주얼 게임을 여러 종류 반복해서 만들어야 하는 상황을 가정하고, "무엇이 정말로 공통이고 무엇이 장르마다 다른가"를 **미리 설계로 추측하지 않고 실제로 4개 장르를 만들어보면서 검증**하는 방식을 택함. 섣부른 추상화(예: 인터랙션 모델을 억지로 공통 인터페이스로 묶기)를 피하고, "3번 이상 반복된 것만 승격한다"는 원칙을 실제로 지킴 — 예를 들어 인터랙션 모델(드래그+인접판정 / 탭+좌표히트테스트 / 탭+인덱스스왑 / 탭+쌍비교)은 4개 장르 모두 코드를 한 줄도 공유하지 않는 것으로 결론 내리고 공통화를 포기함.

## 만든 것

1. **직소 퍼즐 (Puzzle Pals)** — 성인 타겟 16레벨 직소 퍼즐. 이 프로젝트의 베이스가 된 1번째 게임.
2. **틀린그림찾기 (SpotTheDifference)** — 2번째 게임. 좌표 히트테스트 기반 판정.
3. **슬라이딩 퍼즐 (SlidingPuzzle)** — 3번째 게임. **구현 전에 Game Rule Spec을 먼저 문서화하고, 그대로 구현하는 워크플로우 자체를 검증**하기 위해 의도적으로 스펙-퍼스트로 진행.
4. **메모리 매칭 (MemoryMatch)** — 4번째 게임. 위 3개 게임에서 얻은 결론을 스크립트(`bootstrap_project.sh`, `verify_project.sh`)로 자동화한 뒤, 그 자동화가 실전에서 통하는지 검증하기 위해 만든 실증용 게임.

각 게임은 5개 씬(MainMenu/LevelSelect/Gameplay/Complete/Gallery) 구조를 공유하고, IronSource(LevelPlay) 광고 SDK, Unity Localization(4개 언어: ko/en/ja/zh-Hans), Unity IAP, DOTween을 사용.

## 핵심 기술적 결정과 그 이유

- **공용 레이어(Core Spec) 100% 무변경 재사용 확인**: `SceneLoader`, `BackButtonHandler`, `GameManager`, `SaveManager`, `AdManager`(+`IAdProvider` 추상화로 광고 SDK 의존성 분리), `AudioManager`(외부 오디오 에셋 없이 절차적 합성으로 SFX 생성), `HintManager`가 4개 게임 내내 **코드 수정 없이** 파일 복사+네임스페이스 치환만으로 재사용됨. 실제로 새로 작성해야 했던 코드는 매 게임마다 딱 3가지(LevelDataSO 서브타입, 게임보드 MonoBehaviour+분리된 순수 로직 클래스, 소스 데이터 Importer)로 좁혀짐.
- **의도적으로 추상화하지 않은 영역**: 인터랙션 모델(입력 처리 방식)은 장르마다 완전히 다르다는 걸 확인하고 공통 인터페이스 시도 자체를 하지 않음 — "괜히 무리하게 합치면 나중에 다 뜯어내야 한다"는 판단을 실제 4회 반복으로 검증.
- **힌트 시스템 설계**: `OnHintRequested` 이벤트 + 재화 차감(`ConsumeHint()`)을 분리한 2단계 구조 채택 — 힌트 재화 관리 로직과 장르별 힌트 효과를 완전히 독립시켜서, 힌트 매니저 코드 자체는 4개 게임 동안 단 한 줄도 안 바뀜.
- **완료 판정 로직**: `progress(foundCount/total) + onComplete 이벤트` 인터페이스는 공통이지만, 트리거 시점(연속 드래그는 프레임 폴링, 이산 탭은 상태변경 시 동기 발행)은 장르 룰에 위임 — "인터페이스는 공통, 호출 타이밍은 장르별"이라는 경계를 명시적으로 그음.
- **테스트 가능하게 만들기 위한 관심사 분리**: 판정 로직을 MonoBehaviour에서 분리한 순수 C# 클래스(`DiffRegion.IsHit`, `SlidingGridState`, `MemoryMatchState`)로 뽑아내야 유닛 테스트가 가능하다는 걸 매 게임에서 재확인 — 테스트 용이성을 아키텍처 결정 기준에 포함시킴.
- **디스플레이 없이 실제 조작 흐름(E2E)까지 자동 검증하는 테스트 기법**: `IPointerClickHandler.OnPointerClick()`을 GameObject에 직접 호출해서 Unity의 EventSystem 레이캐스팅을 우회 — 실제 화면 렌더링 없이 `-batchmode -nographics`로 "탭하면 상태가 올바르게 바뀌는가"까지 배치모드에서 완전 자동 검증. 셔플/랜덤 요소가 있는 장르는 게임보드에 "지금 상태 기준 유효한 조작 대상을 질의하는" 테스트 전용 메서드(`DebugGetAdjacentPieceIndex()` 등)를 추가해서 결정론적 검증이 가능하게 함.
- **알려진 함정을 기록해서 반복 방지**: DOTween의 UI 확장 모듈(`RectTransform.DOAnchorPos` 등)이 이 프로젝트 배포판엔 없어서 컴파일 에러가 나는 문제를 `DOTween.To(getter, setter, ...)` 코어 API로 우회하는 패턴을 확립하고 문서화 → 이후 게임에서 동일 실수 재발 안 함.

## 자동화 — 스크립트 2개

- **`bootstrap_project.sh`**: 가장 최근에 완성된 프로젝트를 rsync로 통째로 복제 + 네임스페이스 일괄 치환(sed) + asmdef 파일명 변경 + `ProjectSettings.asset`의 productName 수정까지 한 번에 처리. "빈 프로젝트에서 새로 시작"보다 "완성된 프로젝트를 복제"하는 쪽이 크로스커팅 요소(SafeArea 처리, Settings 진입점 등) 누락 위험이 없다는 실증 결과를 그대로 스크립트화한 것.
- **`verify_project.sh`**: 컴파일 확인 → 임포터/씬세팅/로컬라이제이션/오디오 파이프라인을 `-executeMethod`로 순차 실행 → EditMode 유닛 테스트 → PlayMode E2E 테스트까지 한 줄로 배치 실행하고, Python으로 결과 XML을 파싱해서 pass/fail을 요약. 4번째 게임(MemoryMatch)에서 실전 투입 시 스크립트 버그 없이 1회차에 바로 성공.
- 두 스크립트 다 실제로 3개 프로젝트(SpotTheDifference/SlidingPuzzle/MemoryMatch)에 대해 라이브로 실행해서 검증 완료.

## 정량적 성과

- **테스트**: 4개 게임 합산 총 134개 자동화 테스트(EditMode 105개 + PlayMode E2E 29개), 전부 통과. 직소 43(32+11), 틀린그림찾기 23(17+6), 슬라이딩 퍼즐 40(34+6), 메모리 매칭 28(22+6).
- **코드 규모**: 4개 프로젝트 합산 C# 스크립트 173개, 테스트 파일 25개.
- **제작 시간 단축 (파일 타임스탬프 기준 실측, 사람이 읽고 생각한 시간 제외)**:
  | | 1번째(직소, 기반 프로젝트) | 2번째(틀린그림찾기) | 3번째(슬라이딩 퍼즐) | 4번째(메모리 매칭) |
  |---|---|---|---|---|
  | 총 작업 구간 | 약 19일(9개 작업일, 04-14~05-03) | 142분 | 44분 | 9분 |
  | 활동 시간 | **정확히 산정 불가 — 약 3.5시간(5분 캡 하한선) ~ 약 29.6시간(상한선) 사이** | 약 69분 | 약 25분 | 9분 |

  \* 파일 수정 사이 공백이 5분을 넘으면 그 이상은 활동 시간에서 제외하는 방식(5분 캡)으로, 회의/디버깅 대화나 배치모드 대기시간을 순수 작업 시간과 분리해서 측정 — 2~4번째는 이 방식이 잘 맞았음(대화 로그로 공백의 성격을 교차검증 가능했으므로). 1번째는 원래 05-03 이후 3개월 뒤(08-02)에 재실행 이슈를 고친 기록도 있었지만, 이건 신규 구현이 아니라 방치 후 재개 시 stale 참조를 재컴파일로 고친 것뿐이라 이 집계에서 제외함.
  → 1번째(직소)는 이 프로젝트의 "재료"가 아니라 **전제조건**이었다는 점이 핵심: Unity/게임 제작 기본기를 직접 익히고 실기기 검증까지 마친 결과물이 있었기 때문에, 2번째 게임부터 "무엇이 진짜 재사용 가능한가"를 판별하는 작업이 가능해짐. 2→3번째는 그렇게 확정된 공용 레이어 재사용 효과, 3→4번째는 스크립트 자동화 + 반복 숙련도가 함께 작용. 단일 요인으로 과대해석하지 않도록 원인을 구분해서 기록함.
  → **1번째만 "활동 시간"을 단일 숫자가 아니라 범위로 표기함.** 당시에도 코드 작성 자체는 에이전트가 담당했지만(현재 접근 불가능한 별도 계정이라 대화 로그로 교차검증 불가), 5분 캡을 그대로 적용하면 실제로는 26시간 분량의 공백을 전부 잘라내고 3.5시간만 남기게 됨 — 이게 진짜 대표값이라 보기 어려움. 사용자 본인 체감상으로도 "더 오래 걸렸다"는 쪽이라, 상한선(29.6시간)에 더 가깝게 보는 게 맞음. **이력서 문구화 시 이 범위나 개별 숫자를 그대로 인용하지 말고**, "제작 시간이 반복될수록 단축됐다"는 2~4번째 추세를 강조하는 근거로만 쓸 것.
  → 4번째(9분)는 "에이전트가 코드를 쓰고 스스로 배치검증까지 마치는 시간"만 잰 수치다. 그 구간 안에는 사람으로 인한 지연이 전혀 없었지만(전 구간이 1~3분 간격으로 연속), 그 직후 사람이 실기기/에디터로 직접 플레이해보고 피드백 3건(완료화면 스포일러/난이도/힌트)을 찾아내는 약 22분은 의도적으로 이 수치에서 분리해뒀다 — "자동 검증"과 "사람의 최종 판단"의 경계를 수치에서도 명확히 유지.
- **문서화**: 6개 섹션(Core Spec/Game Rule Spec 10항목 체크리스트/에셋 파이프라인/에이전트 오케스트레이션 8단계/검증 체크리스트/신규 게임 요청 가이드)으로 구성된 368줄 설계 문서를 프로젝트 진행과 동시에 계속 갱신 — 사후 정리가 아니라 매 게임 완료 직후 "스펙과 실제가 어긋난 지점"을 즉시 기록하는 방식으로 운영.

## 사용 기술 스택

Unity 6000.4.2f1, C#, 2D URP, Unity Input System, Unity Localization, Unity IAP, DOTween, IronSource(LevelPlay) 광고 SDK, NUnit(EditMode/PlayMode 테스트), bash 스크립팅, Python(테스트 결과 XML 파싱), git 없이 파일시스템 기반 버전 관리(rsync 기반 프로젝트 복제).

## 이력서 문구화할 때 강조할 수 있는 포인트 (재료 — 아직 다듬어지지 않은 원료)

- **아키텍처 설계 근거를 실증으로 확보**: 설계를 먼저 정하고 끼워 맞춘 게 아니라, 4개 장르를 실제로 구현한 뒤 "무엇이 코드 수정 없이 재사용됐는가"를 근거로 공통/개별 경계를 사후에 확정. 섣부른 추상화를 피하는 판단력.
- **테스트 자동화 범위를 스스로 넓힘**: "화면이 없으면 실제 조작감은 사람이 볼 수밖에 없다"는 전제를 그대로 받아들이지 않고, 인터페이스 직접 호출 기법으로 디스플레이 없는 환경에서도 실제 탭→판정 흐름을 E2E로 자동 검증하는 방법을 찾아 4개 프로젝트 전부에 적용.
- **반복 작업의 스크립트화 타이밍 판단**: 2개 게임을 손으로 반복한 뒤에야 스크립트화를 진행 — 패턴이 실제로 안정적으로 반복되는지 확인 후 자동화하는 순서를 지킴(성급한 자동화로 잘못된 패턴을 고착시키는 리스크 회피).
- **문서를 살아있는 스펙으로 운영**: 매 게임 완료 후 실제 플레이 피드백(예: 힌트가 카드 한 장만 보여줘서 무의미했던 문제, 완성 이미지가 없는 장르에서 기존 Complete 화면 패턴이 안 맞았던 문제)을 구현 완료가 아니라 "스펙 공백"으로 기록하고 다음 장르 착수 전 체크리스트로 승격.
